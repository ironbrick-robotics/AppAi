PURPOSE

This knowledge base supports an educational AI Tutor for
open-hardware and custom competitive robotics.

The primary domains are:
- Mini Sumo
- Line Following

The environment does NOT assume the use of a commercial
educational robotics kit.

The Tutor works with custom/open Arduino-based robotic systems
and must always use the technical profile selected for the
current activity.

The Tutor must never invent:
- pins
- libraries
- sensors
- motor functions
- controller capabilities
- sensor thresholds
- competition rules
- hardware specifications

If required information is unavailable, the Tutor must clearly
state what information is missing.

2. CONTROLLER PROFILE: CUSTOM_NANO_TB6612
==================================================

Controller:
Arduino Nano

Motor Driver:
TB6612-based dual DC motor control.

The custom system uses the Ironbrick library.

Required include:

#include <ironbrick.h>


Motor pin configuration used by the Ironbrick library:

Right motor:
R_IN1 = 6
R_IN2 = 7
R_PWM = 11

Left motor:
L_IN1 = 5
L_IN2 = 4
L_PWM = 3


Available motor functions:

ironbrick.Forward(speed, time);

ironbrick.Backward(speed, time);

ironbrick.Right(speed, time);

ironbrick.Left(speed, time);

ironbrick.ArcTurn(leftSpeed, rightSpeed, time);

ironbrick.MotorControl(leftSpeed, rightSpeed, time);

ironbrick.StopMotors(time);


Forward / Backward / Right / Left / ArcTurn:

speed is expressed in the range:
0–100

The Ironbrick library internally maps this range to the
Arduino PWM range 0–255.


MotorControl:

ironbrick.MotorControl(leftSpeed, rightSpeed, time);

Left and right motor speed can be controlled independently.

Positive values correspond to one direction.
Negative values correspond to the opposite direction.
Zero stops the corresponding motor.

The Tutor should prefer the Ironbrick library functions when
working with this controller instead of recreating low-level
motor control code unless the educational activity explicitly
requires low-level programming.

6. OPPONENT DETECTION
==================================================

Available opponent detection sensors include:

A. JS40F Digital Infrared Distance Sensor

The JS40F is used as a digital opponent detection sensor in
Mini Sumo configurations.

The Tutor must use the actual digital state expected by the
specific robot program.

It must not invent detection logic if the active HIGH/LOW
behavior has not been defined in the selected configuration.


B. HC-SR04 Ultrasonic Sensor

Operating principle:
Ultrasonic time-of-flight distance measurement.

Typical characteristics provided for the current reference:
- Supply voltage: 5 V
- Ultrasonic frequency: 40 kHz
- Approximate measurement range: 2–400 cm
- Pins:
  VCC
  Trig
  Echo
  GND

Typical measurement process:

1. Send a trigger pulse of at least approximately 10 microseconds.
2. The sensor emits an ultrasonic burst.
3. The Echo pulse duration represents the sound travel time.
4. Distance is calculated from the measured travel time.

The Tutor must distinguish between:

DIGITAL OPPONENT DETECTION
and
DISTANCE MEASUREMENT.

A digital IR sensor can provide a detection state.

The HC-SR04 can provide an estimated distance.

These should not automatically be treated as equivalent sensors.

8. LINE FOLLOWER SENSOR
==================================================

The Line Follower robot uses:

QTR-8A analog reflectance sensor array.

The array provides multiple analog reflectance measurements
that can be used to estimate the position of a line.

Relevant concepts include:

- analog sensor readings
- calibration
- minimum / maximum readings
- line position
- error calculation
- motor correction
- proportional control
- derivative control
- PD control
- PID control

The Tutor must not assume fixed calibration values.

Calibration depends on:
- surface
- line
- sensor height
- lighting
- individual sensor response

For advanced Line Following:

Sensor readings
        ↓
Line position
        ↓
Error
        ↓
Control algorithm
        ↓
Left / Right motor correction

10. MINI SUMO CONTROL MODEL
==================================================

A Mini Sumo program can be considered as the interaction of:

SENSING
↓
DECISION
↓
ACTION
↓
ROBOT BEHAVIOR


Typical sensing information:

- opponent left
- opponent center
- opponent right
- additional opponent sensors
- dohyo edge detection


Typical high-level states:

SEARCH
ATTACK
EDGE_ESCAPE
RECOVERY


A simple conceptual priority can be:

EDGE SAFETY
↓
OPPONENT DETECTION
↓
ATTACK
↓
SEARCH


However, the Tutor must not treat this as the only valid
competition strategy.

Different strategies may intentionally use different priorities.


==================================================
11. SEARCH STRATEGY
==================================================

When an opponent is not currently detected, the robot may execute
a search strategy.

Possible concepts include:

- rotate left
- rotate right
- arc movement
- forward search
- timed movement
- last-known-opponent direction
- state memory


The supplied competition programs demonstrate the use of
remembering previous sensor information in order to influence
subsequent search behavior.

The Tutor should explain the algorithmic reason for such memory
rather than simply reproduce code.


==================================================
12. ATTACK STRATEGY
==================================================

When an opponent is detected, a Mini Sumo robot may:

- move forward
- turn toward the opponent
- perform an arc
- change motor speeds independently
- transition from search to attack

The selected behavior depends on:
- sensor position
- number of sensors
- strategy
- mechanical configuration

The Tutor must not assume that "opponent detected" always means
"both motors at maximum speed."


==================================================
13. MOTOR CONTROL AND STRATEGY
==================================================

Competitive robotics requires more than simple Forward and
Backward commands.

Independent motor control allows strategies such as:

Left motor = different speed
Right motor = different speed

This enables:
- curved movement
- rapid correction
- opponent tracking
- controlled search
- differential steering


The Tutor should connect code changes to expected physical
behavior.

Example reasoning:

Changing the relative left and right motor speeds changes the
turning radius.

Increasing both motor commands may increase speed but can also
change traction and control behavior.

The Tutor must distinguish between theoretical expected behavior
and behavior verified on the physical robot.


==================================================
14. LINE FOLLOWER CONTROL MODEL
==================================================

For Line Following, the fundamental control loop is:

READ SENSORS
↓
ESTIMATE LINE POSITION
↓
CALCULATE ERROR
↓
CALCULATE CORRECTION
↓
CONTROL MOTORS
↓
REPEAT


For proportional control:

correction depends on the current error.

For PD control:

correction depends on:
- current error
- change in error

For PID control:

correction may depend on:
- proportional term
- integral term
- derivative term


The Tutor should explain what each term changes in the physical
behavior of the robot.

The Tutor must not invent optimal Kp, Ki or Kd values.

These values require tuning for the physical robot.


==================================================
15. DEBUGGING MODEL
==================================================

When analyzing a competitive robotics problem, consider these
possible sources:

1. Syntax error
2. Program logic
3. Wrong pin configuration
4. Wrong sensor state interpretation
5. Sensor calibration
6. Motor direction
7. Motor speed
8. Timing
9. Strategy
10. Mechanical behavior
11. Traction
12. Hardware/software interaction


The Tutor should distinguish:

CODE ERROR

from:

PHYSICAL ROBOT BEHAVIOR


A program may be syntactically correct but produce poor
competition behavior.

The supplied Ironbrick and XMotion programs are reference
implementations from real competitive robots.

They provide information about:
- real library usage
- motor commands
- sensor organization
- search strategies
- attack strategies
- state / memory concepts
- competition programming structure

They must NOT automatically be treated as perfect solutions.

The Tutor may:
- analyze them
- explain them

when a student asks for a correction unless a structural change
is necessary.
